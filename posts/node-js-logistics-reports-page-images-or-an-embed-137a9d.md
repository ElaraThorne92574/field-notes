# Node.js Logistics Reports — Page Images or an Embedded PDF Viewer

TL;DR: For a monthly logistics report, render page images for the report index and embed a PDF viewer only on the report detail screen. That is the least complex way to keep browsing cheap while preserving searchable text, selectable shipment IDs, links, and fine print when someone opens the document.

| Preview surface | Default representation | Main reason | Main cost |
| --- | --- | --- | --- |
| Report index | First-page image | Predictable, fast scanning | One raster render per report version |
| Report detail | Embedded PDF viewer | Preserves document behavior and fine detail | Browser memory and PDF parsing |
| Email or notification | Small image plus a link | Works without an interactive document runtime | Cannot inspect the full report in place |

**Recommendation:** use both representations, but give each one a narrow job. Converting every page up front wastes compute and storage. Embedding a full viewer in every list row makes the browser parse documents that the user may never open.

## Should you convert each PDF page to an image or embed a viewer?

A dispatcher scanning 40 monthly carrier reports has a different job from an auditor checking a surcharge footnote. The dispatcher needs a stable cover thumbnail, route name, reporting period, generation status, and archive link. The auditor needs zoom, search, text selection, internal links, and every page in the original order.

That distinction matters because PDF is a document format, not a picture container. ISO 32000-2 defines a structured format that can carry pages, text, annotations, metadata, and interactive features. Rasterizing a page deliberately collapses much of that structure into pixels. It can be the right move, but the loss is real. In this design, I accept that loss only on the index because the index is for recognition, not inspection; accepting it on the detail screen would undermine the auditor's job.

Start with the user action. If the preview answers “is this the right report?”, an image is enough. If it must answer “which shipment produced this adjustment?”, keep the PDF available in a dedicated viewer.

No universal winner exists. The surface decides.

The trade-off is concrete.

## Fidelity means more than matching pixels

Image conversion produces a controlled visual snapshot. The host application chooses the width, output format, and compression once, then serves an ordinary image. That makes index layouts easy to size and cache. It also removes selectable text, document search, accessible reading order, annotations, and working links from that representation. An image `alt` value can identify the report, but it cannot reproduce a dense table accessibly.

An embedded viewer retains far more of the document's useful behavior. Browser-native PDF handling varies by environment, though, and an HTML `<embed>` element does not provide fallback content for a browser that cannot display the resource. A production detail page therefore needs an explicit download or open-document link outside the embed. Its limitation is equally plain: it is a poor fit for a dense report index, where dozens of independent document runtimes would consume browser resources before the user chose a report.

There is another boundary: security. Treat uploaded and generated PDFs as untrusted input. Keep the archive object immutable, validate the media type and file signature before processing, and serve previews from a constrained origin with deliberate response headers. Do not let a report filename become an HTML fragment or a storage path. The OWASP file-upload guidance recommends allowlisting extensions, validating file type rather than trusting the `Content-Type` header, changing filenames, limiting size, and storing files away from the web root.

For a logistics report, the fidelity check should use actual hard pages: a landscape lane table, a page with small totals, a page containing links, and the final legal notes. A pretty cover proves very little.

## Render cost starts with invalidation

Render cost is not just CPU time. It includes queue time, decoder memory, generated bytes, object-store operations, cache misses, and the engineering work required to retry partial jobs. Measure those separately. A single “preview latency” chart hides the expensive part.

The useful unit is a report version. A hypothetical 120-page report does not need 120 images merely because it was archived. Generate the first-page thumbnail after the PDF becomes immutable. Render another page only when the interface has a real image-only use for it. Key derived assets by the source digest plus render parameters, so changing the width or format creates a new object rather than silently mutating an old cache entry.

**Do not render on every request.** Put conversion behind an idempotent job, cap its memory and execution time, and record the source digest, page number, dimensions, duration, output bytes, and outcome. Those fields let a team compare fidelity and cost without inventing a synthetic score.

Benchmark with the documents the system will archive. Record cold and warm runs separately, and include malformed and unusually large inputs. I would reject a decision based only on a one-page sample: it says nothing about table-heavy monthly reports, concurrency, or tail behavior. Publish the fixture set and command alongside the results so another engineer can reproduce them.

## Keep the Node.js boundary small

Application code should request a preview, not know which renderer executable or library produced it. A narrow interface keeps storage, queueing, and conversion replaceable while making cache rules obvious.

```ts
type PreviewSpec = Readonly<{
  page: number;
  widthPx: number;
  format: "webp" | "png";
}>;

type ArchivedReport = Readonly<{
  reportId: string;
  sourceDigest: string;
  pdfObjectKey: string;
}>;

interface PreviewRenderer {
  render(report: ArchivedReport, spec: PreviewSpec): Promise<Uint8Array>;
}

function previewObjectKey(report: ArchivedReport, spec: PreviewSpec): string {
  if (!Number.isInteger(spec.page) || spec.page < 1) {
    throw new RangeError("page must be a positive integer");
  }
  if (!Number.isInteger(spec.widthPx) || spec.widthPx < 1) {
    throw new RangeError("widthPx must be a positive integer");
  }

  return [
    "report-previews",
    report.sourceDigest,
    `page-${spec.page}`,
    `${spec.widthPx}.${spec.format}`,
  ].join("/");
}

async function ensurePreview(
  report: ArchivedReport,
  spec: PreviewSpec,
  renderer: PreviewRenderer,
  exists: (key: string) => Promise<boolean>,
  put: (key: string, body: Uint8Array) => Promise<void>,
): Promise<string> {
  const key = previewObjectKey(report, spec);
  if (await exists(key)) return key;

  const body = await renderer.render(report, spec);
  await put(key, body);
  return key;
}
```

The example omits the distributed lock on purpose because its correct shape depends on the queue and object store. In a real deployment, two workers may miss the same key at once. Either tolerate duplicate deterministic writes or acquire a lease keyed by the derived object name; never rely on an in-process mutex across replicas.

Keep the original PDF as the archive record. A thumbnail is a derivative, so it should be disposable and reproducible from an immutable source. If retention policy removes the source, remove its derivatives through the same lifecycle rather than a separate hand-maintained cleanup list.

## Test the failure paths, not just the cover

Golden-image comparisons can catch clipping, missing fonts, transparency changes, and incorrect rotation. Use a small tolerance because renderer and font updates may change antialiasing without changing meaning. Pair that check with text-level assertions against the source PDF where extraction is part of the workflow; a visually plausible thumbnail cannot prove that the archived document is searchable.

Operationally, track conversion attempts, failures by reason, render duration, peak memory, output size, and cache-hit ratio. Alert on sustained failure rates and queue age, not a single slow report. Put a dead-letter path around inputs that repeatedly fail, then expose a clear “preview unavailable” state with access to the original PDF when policy permits.

The detail viewer needs its own tests: keyboard access, zoom at narrow viewport widths, download behavior, authorization on byte-range requests, and fallback navigation when inline PDF display is unavailable. HTTP range requests are standardized, and PDF viewers commonly use them to retrieve portions of a document. Confirm that the storage or application layer handles ranges correctly instead of assuming the browser downloaded the whole file.

Also test replacement. If a monthly report is regenerated, its digest and derived keys must change together. Serving last month's cached cover beside this month's metadata is worse than showing no preview.

## When is the runner-up the better default?

Use an embedded viewer as the primary preview when most sessions involve reading several pages, searching shipment identifiers, copying values, following document links, or using assistive technology with tagged PDFs. The extra browser work serves the actual task in those cases. A first-page image can remain a loading placeholder, but it should not masquerade as the document.

Choose page images throughout when the surface cannot host a PDF runtime, when the output must fit a fixed visual grid, or when policy requires a deliberately flattened derivative. This approach is not suitable when users must search or select text, and rasterizing every page multiplies derived storage and conversion work. The choice needs pagination controls, clear page counts, useful alternative text outside the image, and a route to the source document if users are authorized to retrieve it. Rendering on demand is reasonable for rarely opened pages, provided the interface shows a bounded processing state and the job is deduplicated. The opposite compromise applies to the viewer: preserve document behavior, but pay the parsing and memory cost only after a reader opens the detail view.

The decision rule stays simple: image conversion is for scanning and constrained surfaces; an embedded viewer is for reading and inspection. For monthly logistics reports, a thumbnail index plus a dedicated PDF detail view preserves the right fidelity without paying to rasterize pages nobody opens.
